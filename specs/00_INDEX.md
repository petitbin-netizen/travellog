# 명세 문서 사용법 (TravelLog-App)

STEP 문서는 전부 **같은 8구역**으로 되어 있습니다. 한 번만 익히면 나머지는 똑같습니다.

---

## 1. STEP 지도 — 결정은 전부 합쳐 21개

| STEP | 이름 | 정하는 것 | 결정 수 | 파일 |
| --- | --- | --- | --- | --- |
| 1 | 입력과 기록 구조 | 기록 한 건에 무엇을 담고, 어디에 저장하나 | 3 | [01](01_INPUT_AND_STYLE.md) |
| 2 | 페이지 구성안 | 화면이 어떻게 생겼나 (핀터레스트 감성) | 3 | [02](02_PAGE_DESIGN.md) |
| 3 | 정보량 카운트 | 몇 개·몇 자면 완성인가 (숫자만) | 4 | [03](03_INFORMATION_COUNT.md) |
| 4 | 경계·작업·안전 | 어디까지 맡기고 언제 끼어드나 | 3 | [04](04_BOUNDARY_TASKS_SAFETY.md) |
| 5 | 테스트와 검증 | 무엇이 PASS를 판정하나 | 3 | [05](05_TEST_AND_VERIFIER.md) |
| 6 | 반복 방법 | 실패하면 무엇을 하나 | 3 | [06](06_LOOP_ITERATION.md) |
| 7 | 실행 계약 | 무엇이 되면 끝인가 | 2 | [07](07_EXECUTION_CONTRACT.md) |

---

## 2. 이 프로젝트가 만드는 것

```text
                  ┌─────────────────────────────────────┐
   내가 답한다 ──▶ │  STEP 1~7 명세 (질문 21개)          │
                  └──────────────┬──────────────────────┘
                                 │ 모임
                                 ▼
                  ┌─────────────────────────────────────┐
                  │  MASTER_SPEC.md                     │
                  │    count_contract  기록 스키마·분량  │
                  │    page_contract   목록/상세/입력 화면│
                  └──────────────┬──────────────────────┘
                                 │ 읽음 (STEP 5 승인 직후 한 번 생성 후 잠금)
                                 ▼
                  ┌─────────────────────────────────────┐
   루프가 돈다 ──▶ │  검사기 (부트스트랩 후 잠김)          │
                  │    루프 A  기록 정보량을 다 채웠나    │
                  │    루프 B  화면을 다 채웠나          │
                  │    루프 C  정성 3회를 돌았나          │
                  └──────────────┬──────────────────────┘
                                 ▼
                output/  (브라우저 웹앱 한 벌 · 서버 없음)
                  index.html · app.js · style.css · data/records.json
```

---

## 3. 루프는 세 바퀴다

```text
   루프 A 정보량 충족 → 루프 B 화면 완성 → 루프 C 정성 완성도
        └─ 먼저 끝나야 함 ─┴─ 먼저 끝나야 함 ─┘

   각 바퀴가 끝나면 나에게 되물음이 뜹니다.
```

| 바퀴 | 끝나는 조건 | 누가 정하나 |
| --- | --- | --- |
| A 정보량 | 검사기 통과 (상한까지) | 교육생 |
| B 화면 | 검사기 통과 (상한까지) | 교육생 |
| **C 정성** | **정해진 3회를 돌면** | **킷 고정** |

> 정성은 점수로 닫을 수 없습니다. 글을 쓴 쪽이 자기 글에 점수를 주기 때문입니다.
> 규율은 [QUALITY_RUBRIC](QUALITY_RUBRIC.md)에 있습니다 (핀터레스트 감성 10가지).

## 4. 읽는 순서 — 모든 STEP이 똑같다

| 번호 | 구역 | 누가 쓰나 | 읽는 법 |
| --- | --- | --- | --- |
| `1` | 이 STEP에서 정하는 것 | 이미 작성됨 | 30초 |
| `2` | 앞에서 물려받은 결정 | Claude가 채움 | 확인만 |
| `3` | 이미 정해 둔 것 | 이미 작성됨 | 훑고 넘어가기 |
| `4` | 내가 결정할 질문 | 고정. 수정 금지 | 여기서만 고민 |
| `5` | 내 답 적기 | 교육생 | 고른 것을 적는다 |
| `6` | Claude가 정리한 결과 | Claude가 채움 | 확인만 |
| `7` | 이 STEP이 끝나면 무엇이 진행되는가 | 이미 작성됨 | 다음에 뭘 할지 여기 있다 |
| `8` | 완료 확인과 다음 명령 | 함께 확인 | 체크리스트 |

## 5. 결정 ID 읽는 법

```text
좋음   D-기록스키마      기록 한 건의 필드 구성
좋음   TASK-데이터스키마정의
나쁨   D-008             무엇을 정했는지 알 수 없다
```

| 종류 | 형식 | 규칙 |
| --- | --- | --- |
| 결정 | `D-이름` | 한글 2~16자. 숫자만 쓰지 않는다 |
| 작업 | `TASK-이름` | 이름이 곧 하는 일 |
| 테스트 | `TEST-이름` | 검사하는 바퀴의 이름을 쓴다 |

문서 안에서 ID는 항상 백틱으로 감쌉니다.

---

## 6. 문서 안의 표시(마커)

| 마커 | 뜻 | 누가 고치나 |
| --- | --- | --- |
| `FIXED` | 고정 질문. 문장을 바꾸지 않는다 | 아무도 |
| `ANSWERS` | 교육생이 답하는 칸 | 교육생 |
| `PROJECT` | 결정이 반영되는 칸 | Claude |
| `MACHINE` | 스크립트가 읽는 JSON | Claude |
| `STATUS` | 현재 상태 한 줄 | Claude |
| `EXAMPLE` | 예시. 검사에서 제외 | — |

`(미작성)`이 남아 있으면 아직 답하지 않은 것입니다.

---

## 7. 상태값 6가지

```text
DRAFT · IN_PROGRESS · READY_FOR_REVIEW · APPROVED · NEEDS_REVIEW · BLOCKED
```

**필수 결정이 비어 있으면 `APPROVED`로 바꾸지 않습니다.**

---

## 8. 진행하는 법

```text
STEP 1 진행해줘      ← 이렇게만 말하면 됩니다
```

**STEP 7이 끝나면** [결정 장부](00_DECISION_LOG.md)에 내가 고른 21개가 만든 루프 구조도가 그려집니다.

---

## 9. 확인 명령

| 명령 | 무엇을 보나 |
| --- | --- |
| `python scripts/validate_specs.py --step 3` | 문서 구조가 맞는가 (한 STEP) |
| `python scripts/validate_specs.py` | 문서 구조가 맞는가 (전체) |
| `python scripts/check_loop_readiness.py` | 루프를 시작해도 되는가 |
| `python scripts/verify_all.py` | 루프가 끝났는가 — 세 바퀴 전부 |

> 이 프로젝트는 **아직 `scripts/` 안이 비어 있습니다.** STEP 5 승인 직후,
> 명세만 보고 이 스크립트들을 한 번 만들고 그 즉시 잠급니다. (`CLAUDE.md` 5번)

---

## 10. 이미 승인한 결정을 바꾸고 싶다면

조용히 덮어쓰지 않습니다. "D-기록당장소수를 2개에서 3개로 바꾸고 싶어"처럼 말하면,
영향 범위를 표로 보여 주고 결정 장부에 이전 값·새 값·이유·시각을 남깁니다.
